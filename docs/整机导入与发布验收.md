# Time-cut Windows 整机导入与发布验收

目标是让用户将 iPhone 接入一次，收齐 Windows 通过 USB 提供的原件后即可拔线，电脑独立完成去重和相簿整理。照片、视频、实况照片的两个文件及编辑附件都要计入来源清单。相簿中合并显示的数量和磁盘上的文件数量分别记录。

## 开发顺序

| 阶段 | 交付内容 | 验证方法 |
| --- | --- | --- |
| 1 · 接收与恢复 | 在每个完整列出的目录中优先取回本机缺少的文件。继续使用旧图库和持久收件记录。文件版本不明时，边接收边计算摘要，在同一次读取中比较或保存。遇到来源错配或版本无法确认时，重新打开数据流并独立核对。 | 模拟同名同大小异内容、对象标识变化、只读到部分目录、传输被中断、重启，以及接收期间手机内容变化。检查实际打开源文件的次数和本地结果。 |
| 2 · 整机清单 | 保存逐目录盘点、逐项凭据、历史待补记录和失败位置。进度区分别显示已经盘点的范围、确有凭据的数量及尚需核对的数量。 | 同一台手机、同一图库连续观察。按文件大小和摘要核验原件。清单不完整、文件有变化、存在未解决的读取错误，均应保留未完成状态。 |
| 3 · 拔线与离线整理 | 所有来源项目都有本地凭据且复核成功后提示拔线，记录起止时间。后续归档、配对、时间、地点、人物和分类在电脑上独立运行。 | 记录真实可拔线耗时。本轮手机保持可用时自动复扫，要求同一清单、新增零、失败零。对归档文件和相簿索引逐项对账，抽查照片和视频能打开，保留用户原有编辑。 |
| 4 · 回归与整体验收 | 运行原生、前端、文件夹导入、进程中断恢复、桌面端到端和发行包测试。 | 记录测试环境、跳过项目及其实际替代验证。若 Windows 接口持续读不到完整来源，检查系统对照入口和可用的独立接收路径，保留既有证据。 |
| 5 · 审计与公开发布 | 对运行正常的候选版审查全项目代码、桌面视觉与操作流程。清理可重建的过程文件，保留用户图库、源码、许可及验收所需证据。 | 从干净检出验证构建、下载及解包；审核公开内容、依赖来源和许可、更新地址、工作流和归属。提交到新公开 GitHub 仓库，打对应提交的标签，发布经核验的 Windows 包和 SHA-256，再从公开入口下载复核。 |

## 真机测量口径

### Apple 原件目录与 Windows 照片接口分别恢复时

1. 在原图库对照 Windows 照片接口、Apple 设备服务和实际可打开的 DCIM 目录。保留这台手机最近一次完整清单、已接收的本地文件和未核对的旧版本。精确匹配来源、版本、路径和长度的旧凭据可在本地校验后补入进度。
2. 只有 Apple 服务识别到一台已配对的 iPhone 时，新图库可直接从 DCIM 接收。若图库对同一部手机已有未完成的 Windows 清单，同时保留两套清单。目录枚举中途退出，即使当时发现的文件都已落盘，仍须恢复并走完目录。
3. 对 Apple 原件的验收复扫要与该图库上一次成功接收的清单逐项对照，重新检查本地文件。清单相同、新写入零份且缺失为零时，单列 Apple 原件复扫结果。Windows 已看见但尚无本地凭据的项目继续待核对。只有本次接收涉及的来源都已收齐，才给出整机拔线时间。
4. 用真实连接测量首份新照片、可拔线时间、离线整理完成和整机零新增复扫。确认现有图库里的照片、视频、实况配对与编辑附件后，再开始第 5 阶段的审计和公开发布。

首次新文件落盘、首次安全拔线、离线整理完成、零新增复扫是四个独立时点。需注明测试起始时图库是否已有备份，以及本次经过时间是否包括等待设备或更新应用。发现的目录数可以先显示。只有完整的来源清单才作为整机进度的分母。

### 验证中断后返回的文件

真机对照中，Windows 能返回所请求文件的名称和大小，随后提供的数据却与上一个请求对应的本地原件摘要相同。对照使用了分别打开的只读会话。大小异常仍须作为读取失败处理。相同大小的两份不同文件也要覆盖到回归测试中。

### USB 导出格式变化时如何核对原件

在同一台手机、同一图库的一次真机复查中，21 个重新列出的目录包含 6,950 个上次清单里没有的 JPG 路径。每项在上次清单中都有一份已取得凭据的 HEIC，与这次 JPG 的父目录、主文件名、设备持久标识和修改时间全部相同。6,950 项的大小全部改变，重新列出的对应目录均未同时提供那份 HEIC。这解释了按导出路径和大小恢复时，大量已经备份的拍摄内容为何重新进入待核对队列。Apple 说明，经 USB 导入时 HEIF 可能被转换成 JPEG。[Apple 的 USB 格式说明](https://support.apple.com/zh-cn/116944)

接下来要分别核对实际缺少的原件和 Windows 更换了格式的导出项。先处理找不到原片候选的照片、视频和附件，导出格式发生变化的项目保留独立记录。对格式变化的照片，用同一设备的原片接口或原片模式复读并核对本地摘要。验收要覆盖同一原片更换导出格式、共存的独立 JPEG 和 HEIC、拍摄后编辑、文件标识复用，以及切换接口后部分目录仍不可读。收齐提示应能追溯到完整的手机原件清单和每份原件的本地校验记录。

实机从「自动」改为「保留原片」后，保持数据线连接并重新打开了读取会话。之后重新盘点到了之前选定的全部 6,950 份对照照片。Windows 对这批照片仍然只列出 JPEG。独立核对了 8 对已收到的 JPEG 和旧 HEIC，文件摘要均正确，每对解码后的缩小图像吻合。另抽取 5 对相同设备标识、路径和修改时间的 MOV，文件探测显示早期备份均为 HEVC，新收到的均为 H.264。四对视频时长一致，一对相差约 0.033 秒。

如果设备先变更文件标识，再变更传输格式，上一份完整清单仍可能记录了新标识对应的原始文件名。接收器保留这些原始格式的目录记录，并检查本地是否有路径、大小和修改时间均吻合、内容唯一的已备份候选。该关系仅用于安排取件顺序。图库所在卷的可用空间小于这批待查 JPEG 和 MOV 的预计总量时，程序暂缓下载这批文件，继续接收其他素材。测试要覆盖未写入的文件保持待补、独立 JPEG 和视频继续接收、来源清单替换后仍可找到原始格式记录，以及候选没有被计为已验证。

恢复传输时，先用当前清单中两份内容不同、已有版本凭据的小文件核对手机响应。取得这两份凭据前，对缺少可靠凭据的内容重新打开数据流并比较完整摘要，发生差异即丢弃临时文件。验收时分别记录磁盘内容校验、来源对应关系和清单覆盖。若 Windows 持续返回错误资源，须用独立的原件读取接口取得对照；单纯增加重试次数不能证明整机收齐。

按已保存的清单续导时，每次先处理一批待核对文件，再读取此前已核实的两个对照文件。这样即使某个对照文件无法读取，其他文件也能陆续取得凭据。两个对照都通过后，如果手机传来的完整内容与该路径、该大小下的全部历史摘要一致，即可复用本地原件。新内容、改动和跨文件名匹配仍需两次独立读取。回归测试覆盖了对照文件返回同长度错误内容、同大小照片被编辑，以及改名后内容重复三种情况。

这台 iPhone 的日志中有 30 次短传输，实际字节数都与电脑上对应 HEIC 的长度一致。在两组交替请求的真机对照中，一次请求 JPEG 得到了同一照片的 HEIC，完整摘要与本地原件一致。另几次请求虽能核对目录、版本和时间，拿到的却是前一请求的内容。待查条目要保留设备声明的文件和实际返回的数据两份记录。相同主文件名、时间或预期长度只能帮助寻找候选原件，单凭这些字段不能签发收齐提示。

私有验收在现有图库上进行。公开报告使用汇总数量、时间、字节和错误类别，测试样例使用合成素材。设备序列号、原件、缩略图、地理位置及可识别的目录清单保存在本机。

同一个标为 2,737,917 字节 JPEG 的真机条目在两个独立会话中都返回 1,190,399 字节。每次先取两份已知内容不同的对照文件，第二次调换顺序，再读取目标；读取前后均核对来源对象。两次数据的完整 BLAKE3 都与电脑上该照片的 HEIC 原片一致。每轮的最后一个请求是目标，以免其响应影响后一份文件。

测试应用将异常读取得到的字节数、完整摘要和核对会话记在图库内。只有能够重新确认所属目录、当前句柄、版本、大小和时间的结果才记录到该文件名下。任意 I/O 错误或一次未读完的传输都不能提供完整摘要。历史记录和界面会区分设备离线、Windows 读取会话中断和来源内容不符。内容异常的记录单独计数，原有的整机收齐条件继续生效。

同一台已配对 iPhone 的交叉核对应检查硬件序列号，使用 Apple 设备服务的普通 AFC 接口取得 DCIM 原始文件名、大小和内容摘要。电脑先用本地文件的 BLAKE3 复核历史凭据，同次读取计算可与手机比较的 SHA-1。硬盘文件被替换、同大小编辑或缺失时须重新验证。独立核对须报告清单稳定性和未找到本地原件的数量，保留 WPD 的历史待查记录。

Windows 照片目录读不到时，桌面接收器可以通过已安装的 Apple 设备服务补收同一台 iPhone 的 DCIM 原件。硬件身份、当前 Windows 接收记录和图库须能对应。每份通过 Apple 发现的原件在请求内容摘要前记入待补清单，电脑复用有完整校验的副本，并补收缺失内容。最终拔线检查同时核对 Windows 清单和额外发现的 Apple 原件。两个来源各自列出数量，Apple 目录补收完成时继续保留 Windows 的未决条目。

### 从已盘清的手机清单续导

接收中断后，使用完整清单记录的持久标识向 Windows 请求当前连接的文件句柄。只有目录、文件名、版本、大小、时间均匹配，且条目可以唯一识别时，才按这条记录取回内容。无法确认的项目留给全目录复扫。一次读取失败后，优先给其他未尝试的项目机会。

目录归属从设备根目录向下枚举，并核对当前目录是否列出了该文件句柄。这台 iPhone 上 9 个对照条目均能按这种方式验证。依赖文件夹返回的上级标识会在同一位置遇到 Windows 读取错误。目录成员缓存只用于当前连接，确认可拔线前仍要重新盘点。

从已知清单选择下一批文件时，按来源路径索引查找重名条目。用应用自带的 SQLite 在同一份 47,782 项清单上做只读对照，原查询用时 194.837 秒，按路径索引查找用时 36 毫秒，选出的 512 条记录及顺序一致。这项测量只涵盖电脑上的调度查询。回归测试用 SQLite 指令数检测重复全表查找。

续导还要检查实际取件顺序。在真机保存的清单中，按原目录顺序重试会先经过 5,659 个已有同路径、同大小候选的项目，然后才轮到第一个没有这种候选的项目。现在每批将首次请求、缺少本地候选的条目与可能已备份的条目交替读取。缺少候选的条目都尝试过后，两组轮流优先，每组按上次尝试的时间重试。这样手机从长时间不可读恢复后，两组都有机会继续。优先级只决定请求顺序，每份内容仍须独立取得有效凭据。

验证时同时记录新核对的来源条目、手机传输字节和本地新增的独有内容。同样的字节以不同名称出现时，保留每个来源的记录并复用已核验的本地文件。临时收件区也要参与比较。保存清单、补齐其中一批文件，以及最终提示拔线，是三个可单独检查的步骤。最终提示仍需全量复核通过。

这台手机最近一次完整清单还包含 4,715 对显示路径相同的 AAE 编辑附件。其中 3,567 对已经分别取得两份内容不同的本地文件。按文件名去重或覆盖会丢失编辑版本。用已收到的一个完整目录做本地回归时，两次文件夹导入覆盖了全部 146 份文件，同路径的 3 对附件都保留了两个版本，13 份附件都能找到对应照片。再次导入当前文件夹后，新增和失败均为零。这项结果覆盖本地文件夹入口，整机复扫需在手机上另行验收。

整机对账还须单列此前见过、本次完整清单不再提供的版本。这台手机有 60 条这样的待补记录，其中 50 条的路径已经消失，10 条在相同路径下列出了其他大小。旧记录保留了当时的路径、时间和大小，现有记录中找不到这 60 个旧版本对应的设备文件标识。若后续盘点能重新列出原版本，应继续补收并核对内容。在此之前，接收报告应单列这 60 条与当前清单内的缺口。

有些文件只在部分连接中可读。接收队列从发现文件时起保留设备提供的版本标识。升级旧图库时，只从同一设备最后一份完整清单中找回能够唯一对应的标识。一次旧记录回查会优先枚举它所在的目录，每四轮续导留出一轮，按上次回查时间轮换。目录完整列出后，仅对文件名、大小和时间唯一匹配、且与已有版本标识相符的候选读取内容。两次独立读取的摘要一致、当前文件仍属于该目录时，才提交收件凭据。找不到文件、出现歧义或传输不完整时，旧记录继续保留。

实机验收分别记录有多少旧项目被安排回查、多少能从手机读到原件，以及复扫覆盖数。使用现有图库的数据库副本演练升级时，13,509 条待补记录中的 13,449 条找回了设备标识，其余 60 条保留为空。升级前后的待补记录、收件计数和当前清单凭据全部一致。

### 区分等待设备和电脑本地工作

Apple 通道的恢复测试覆盖两种中断。一个编辑附件暂时读不到时，其他目录首次出现的照片、视频应继续接收。相机目录暂时无法列出时，可以按上次登记的路径、版本和大小补查少量未收原件，每个成功项目仍须验证内容。再次完整连通后，重新核对所有项目，包括曾经核验过的原件。测试同时覆盖同一版本返回不同字节的情况，两份内容应当保留，拔线提示须继续等待。界面分别显示目录列出的项数、已核对项数和按已知路径补查的结果。

已信任的 iPhone 出现在 USB 列表、相机目录可枚举、文件可打开并校验，是三个分别记录的结果。遇到中断时，在现有图库记录最后一份成功凭据和下一次自动检测时间。用第二个只读客户端复核同一台手机的配对与文件服务，保留错误发生的具体步骤。对 Windows 照片接口同时查看设备问题码、安装状态和驱动安装事件。安装状态为 1 时，Windows 将该接口标记为需要重新安装。驱动有修复记录后，重新检验的仍是实际目录与文件内容。[微软设备安装状态说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/devpkey-device-installstate)

手机仍在设备列表中而相机目录持续为空时，记录最近一次新增原件和最近一次成功核对的时间。待接收空闲后关闭测试应用，再用资源管理器检查同一手机的内部存储，并记录实际列出的项目数。保持手机原有连接，恢复应用时使用同一图库。

场景和人物队列都已处理完时，后台使用同一个只读 SQLite 连接检查图库修订号。图库有提交、用户修改整理选项或索引结束时重新检查。暂时读不到的场景文件保留到期重试，切换或迁移图库时释放观察连接。用同一现有图库对比修改前后时，选取没有接收任务开始或结束的窗口，分别记录进程的逻辑读取量和原件新增数。

在 32,450 项可见素材的测试图库上，旧版的场景和人物空队列查询每轮分别产生约 265 MB 和 129 MB 逻辑读取。桌面进程在旧版的 50.4 秒观察窗口内读取 1.58 GB，在修复版的 50.1 秒窗口内读取 0.90 MB。两次观察期间，手机接收次数和已写入份数均保持不变。

### 验证待确认分类

从现有图库的待确认素材中重新抽取 160 项，139 项得分最高的两个候选是旅行记忆和日常记录。另抽取 32 项已有明确分类的素材作对照。192 项中有 191 项重现了图库里的结果。这个抽样衡量分类复现情况，图库当时没有人工标签。

下一轮分类验证优先检查一段行程中的连续照片。在本机的初步对照中，使用半小时、一公里内至少三个不同分钟的高分照片，并排除目标所在的五分钟区间。对照照片判断一致时，有 2,866 项待确认素材可取得邻近照片的参照。在 857 项已有高分分类的对照素材中，854 项与邻近照片的判断相同，3 项日常记录被推为旅行。人工验收需要覆盖日常外出、旅行和出差等容易混淆的场景，并分别报告各类误判。此次对照没有写入图库分类。
